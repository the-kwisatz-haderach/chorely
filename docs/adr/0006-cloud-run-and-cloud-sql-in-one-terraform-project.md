# Cloud Run and Cloud SQL in one Terraform-managed GCP project

Staging and prod run in one GCP project as two Cloud Run services (request-based billing, 0 to 2 instances) sharing one Cloud SQL Postgres `db-f1-micro` instance, with a database and user per environment, for about $15-20/month. Always-on instances and open WebSockets keep Cloud Run billed, so we avoided both. Neon Launch (about $7/month) is the fallback if the fixed database cost binds. Custom domains use Cloud Run domain mapping rather than a load balancer, which would add about $18/month.

## Consequences

- `infra/modules` holds the reusable pieces: `shared` for project-wide resources (APIs, the SQL instance, Artifact Registry, the GitHub Workload Identity pool) and `environment` for everything one environment owns. `infra/envs/{shared,staging,prod}` are the roots. Environment roots read `shared` outputs from remote state, so `shared` is applied first.
- State lives in a versioned GCS bucket created by hand (`infra/README.md`). Applying is manual; CI only formats, validates and runs `terraform test` with a mocked provider.
- Secret Manager holds containers only. Values are set out-of-band, so they never enter code or state. The database user is created with its password passed as an ephemeral, write-only value read from that secret, so it never enters state either.
- CI owns the image: Terraform creates the service and migration job on a placeholder image and ignores image changes after that.
- Each environment has its own deployer service account, which only GitHub jobs running in the same-named GitHub Environment can impersonate. Prod therefore inherits that Environment's approval. Only staging may push images; prod promotes the same digest and may only read images and move tags. Read access is required, because Cloud Run only deploys an image the deployer can read.
- Deploys run from `.github/workflows/deploy.yml` once CI passes on main. It builds one Next.js standalone image (`Dockerfile`), pushes it, and `.github/scripts/deploy.sh` runs the environment's migration job on it and only then deploys the service, first to staging and then, after approval, the same digest to prod. The image also carries the bundled migration runner, so a revision and its migrations always come from the same commit. Once a newer commit is on staging, the workflow cancels older runs still waiting for prod approval, since they would otherwise hold the prod concurrency group and keep the newer run from reaching approval.
- Migrations are expand/contract: each one must leave the schema usable by the revision before it, and destructive steps (dropping or renaming a column) ship in a later release once nothing reads the old shape. Rolling back is therefore moving traffic to the previous revision; no down migrations exist.
- Staging sets `EMAIL_ALLOWLIST` (Terraform requires it for staging and forbids it for prod), and the app drops mail to any other address, so staging never emails someone who is not testing it. The deploy refuses to run on a staging service without the allowlist.
- Artifact Registry keeps the ten most recent images plus any tagged `prod*`. The deploy workflow tags the image prod runs `prod` and the one before it `prod-previous`, so cleanup never removes prod's image or its rollback target however many staging builds pile up.
- Cloud Run reaches Postgres through the Cloud SQL connector socket. postgres-js cannot take a socket path in a URL, so the socket, user and password come from `PGHOST`, `PGUSER` and `PGPASSWORD`, and `DATABASE_URL` names only the database.
- Cloud SQL makes every user it creates a member of `cloudsqlsuperuser`, which can reach every database. A one-time SQL step (`infra/sql/isolate-environments.sql`, checked in CI) has `postgres` take ownership of both databases and grant each environment's user its own database only, so staging cannot read prod.
- Two instances per environment, each with a pool of five connections, keep both environments and the migration job within db-f1-micro's 25 connections.
- One instance means staging load and maintenance affect prod, and the shared-core tier has no SLA. Both are accepted at household scale.
